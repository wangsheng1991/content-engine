「增强」这个词底下藏着至少四件不同的事：超分、去噪、原地重绘、连构图一起换。它们产出的文件完全不同，而大多数人只告诉你「效果惊艳」，不告诉你跑的是哪一种。

所以我量了一个。不是读宣传页，而是把它公开的示例从命令行拉下来，把输入和输出两个文件都留下，印出两边的 SHA-256。下面是全部结果。

## 这次运行

工具是一个浏览器里的图像增强器；示例是它公开仓库里的一个小脚本，向站点要一份**已经缓存**的样例对 —— 就是访客在页面上点「运行」拿到的那份。不需要账号、不花额度、不上传任何东西：

```sh
node bin/enhance-example.mjs --sample sample1 --out ./out
```

我这次跑的输出（2026-10-30）：

```
catalog: 5033 ms · cached=true
input.jpg     0.15 MiB   812 ms  sha256:19d965fed4699633…
output.webp   0.13 MiB  5377 ms  sha256:229b802a24474dd6…
```

三次 HTTP 请求：目录、输入、输出。**本机没有跑任何模型，也没有扣额度。** 那些毫秒数是网络等待，不是推理耗时 —— 只能说明这三个请求不慢。

## 究竟变了什么

两边都实测，不靠描述：

| | 输入 | 输出 |
|---|---|---|
| 文件 | `input.jpg` | `output.webp` |
| 字节 | 154,319 | 134,222 |
| 尺寸 | 1200×768 | **1200×768** |
| SHA-256 | `19d965fed4699633e9b6faae738fd678592ca5098a47f1535388ef133c2fc28a` | `229b802a24474dd6c8df6ddac02afb454b7563fe3dfcada76c25dfceac89e708` |

![同一帧的输入与输出：滑块在原始 JPEG 与重绘后的 WebP 之间来回切换](assets/before-after.gif)

<small>就是本文量到的那一对：一边是原始 JPEG，另一边是重绘后的输出，同一帧 1200×768。</small>

进出同尺寸。这就是全部结论，它直接排掉了大多数人对「增强」的默认理解：**这不是放大**，是同一帧重画一遍。

站点自己的说明也写死了上限：输出最长边 1536 像素，目标倍率 2 / 4，超出时会降低倍率去适配。所以就算跑你自己的图，这里也不存在「小图变 4K」这条路。

## 两条比数字更要紧的提醒

**一、样本对不能一概而论。** 同一个仓库里的另一份示例，是 1670×1152 的 JPEG 进、1024×1024 的 WebP 出 —— 几何变了，意味着它那对前后对比的滑块不是像素对齐的。判断一个增强器时，先看它给的那对图有没有保住机位：换构图可以美化任何对比。

**二、它不是 NVIDIA 的 DLSS 运行时。** 名字容易误会，所以要说清楚：这里不安装、不替换任何 `nvngx_dlss*` 文件，也不涉及游戏。它只是把你给的图重画一遍再还给你。

## 为什么要贴哈希

落地页上的前后对比图是无法证伪的：你判断不了那张「之后」是工具产出的、别的模型产出的、还是手修的。而文件哈希几年后任何人都能自己验一次。示例之所以附带 `compare.html` —— 一个自带滑块和两边哈希的独立页面 —— 就是为了让这对图可以被复核，而不必相信描述它的 README。

如果你也在做这类东西，最便宜的信任成本就是这套：留下输入、留下输出、把两个哈希都公开，并写清是哪个流程产出的。

## 自己复现

```sh
git clone https://github.com/wangsheng1991/dlss5-visual-enhancer
cd dlss5-visual-enhancer
node bin/enhance-example.mjs --sample sample1 --out ./out
shasum -a 256 out/input.jpg out/output.webp
```

Node 18 以上，零依赖。你算出来的哈希应该和上面那张表一致；不一致就是示例被重新生成过，README 该注明。

想跑**自己的**截图而不是缓存的样例，走站点上的登录流程：每个任务扣 1 额度，注册送额度，1536 像素的长边上限和 2/4 倍率就适用于那条路。
